# Conceptual grounding in Domain-Driven Design

Source reviewed: Eric Evans, *Domain-Driven Design: Tackling Complexity in the Heart of Software*, user-provided PDF attachment. Reviewed Chapter 1 (printed pages 4–13), Chapter 2's opening and Ubiquitous Language discussion (printed pages 14 onward). The provided PDF starts at printed page 3; PDF page numbers differ. The book is not redistributed in this repository.

AGAD adopts these ideas as design interpretation, rather than claiming Evans specifies agent workflows:

- Knowledge crunching is collaborative discovery. Developer–Architect dialogue must combine domain expertise, repository evidence, scenarios and implementation feedback.
- A model becomes useful when behavior and implementation stay connected. The contract records invariants and examples, and review checks their expression in the candidate.
- Shared language belongs in conversations, documents, code and tests. Maintain definitions and rejected ambiguous synonyms; revisit vocabulary when scenarios expose a mismatch.
- Distillation removes irrelevant concepts. An imagined edge case is a question until the developer decides its relevance.
- Learning is continuous. Version the shared model and keep decision rationale, rather than freezing early guesses.

The Architect's role resembles a software modeler collaborating with a domain expert. The human Developer can occupy both software and domain responsibilities. This analogy does not imply that every developer knows every domain fact: external domain uncertainty must remain explicit.

No claims about productivity improvements, benchmark results, or specific harness behavior are imported from earlier discussion without independent evidence.
